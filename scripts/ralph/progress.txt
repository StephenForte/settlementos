## Codebase Patterns
- Read AGENTS.md first — it is the engineering guide (architecture map, invariants,
  gotchas) and CLAUDE.md just points at it. Add durable learnings there, not to a new
  CLAUDE.md.
- Quality gate for every commit: `npm test` (self-contained: compiles contracts, boots
  Hardhat on ports 9545/9546, builds a fresh SQLite fixture under tests/.tmp — never
  touches dev chains or the dev DB), then `npx tsc --noEmit`, then `npm run lint`.
- Run `npm run compile` after ANY contract change — tests read artifacts from
  `chain/artifacts/` (gitignored) and will use stale bytecode otherwise.
- Contract tests: `tests/integration/*.test.ts`, driven with viem via
  `helpers/deploy.ts` (`clientsFor(rpc, chainId)` + `artifact(name)`), fixture accounts
  from `tests/fixture.ts` ACCOUNTS. Assert reverts with
  `await expect(...).rejects.toThrow(/require message/)`.
- A test can deploy its own contract instance against the fixture chain (see the rogue
  token in contract.test.ts) — no need to wire something into global-setup just to test it.
- Addresses read from a contract are EIP-55 checksummed; deployments.json stores them
  lowercase. Lowercase both sides before comparing.
- Money: fiat = decimal strings, on-chain = bigint base units. Never a JS float on-chain.
- Solidity contracts follow one house style: `admin` + `operators` mapping,
  `onlyAdmin`/`onlyOperator` modifiers, constructor makes the deployer both, short
  lowercase revert strings ("not operator").
- No Prisma migrations directory: the schema is applied with `prisma db push`.
  `npm run setup` runs `prisma generate && prisma db push` before seeding, so after
  editing prisma/schema.prisma that is the command that syncs the dev DB + client.
  The test fixture pushes the schema itself in tests/global-setup.ts, so `npm test`
  picks up schema changes with no extra step.
- Demo entities are seeded in TWO places that must stay in sync: `scripts/setup.mjs`
  (dev DB) and `ENTITIES` in `tests/helpers/deploy.ts` (test fixture). Adding an
  Entity field means editing both.
- `npm run setup` needs BOTH local chains up (8545 + 8546) or it exits. To verify it
  without destroying the user's dev state: back up `chain/deployments.json` and
  `prisma/dev.db`, start the chains, run setup, then kill the chains and restore.
- Contract deploys are wired in TWO places that must stay in sync: `setupChain()` in
  `scripts/setup.mjs` (dev chains) and `deployChain()` in `tests/helpers/deploy.ts`
  (test fixture). Anything a new contract needs to be usable — token approvals,
  minted balances — belongs in both, and its address goes in the returned
  `contracts` object so it lands in deployments.json.
- `lib/chain.ts` ABI exports are `as const`, so viem narrows `functionName` to a
  literal union. A test helper taking `functionName: string` will NOT typecheck
  against them — type the param as the union (or cast the ABI to `Abi`).
- Optional per-network contracts resolve through a lookup that returns `undefined`
  instead of throwing (`mmfAddress`), because live testnets legitimately lack them.
  Follow that shape for anything deployed only on some networks.
- The dev server may find :3000 taken and fall back to :3001 — read the actual port
  out of the dev log before curling it.
- `audit()` JSON-stringifies its detail, and JSON.stringify THROWS on a bigint. Convert
  base units to strings before auditing them.
- viem writes return a receipt, not the contract function's return value. Read the
  relevant view before/after (or decode the event) to capture what a mutator returned.
- Contract writes go through the operator helpers in lib/chain: `operatorWrite()` for
  PaymentSettlement, `mmfOperatorWrite()` for TokenizedMMF. Don't hand-roll a wallet.
- Tests that move fixture funds (parking, minting, accruing) must unwind at the end —
  the chains, the DB, and the MMF are shared across test files, which run sequentially.
- lib/treasury throws only `TreasuryError` with a typed `code` — add a code to the
  `TreasuryErrorCode` union rather than throwing a bare Error, so US-007's routes can
  map cause -> HTTP status in one place. Tests assert with
  `.rejects.toMatchObject({ code: "..." })`.
- Rows that model financial history (TreasuryPosition, AuditEvent) are append-only:
  update status in place (ACTIVE -> RECALLED), never delete. Derive current value
  (shares x live index) instead of storing a mutable balance.
- MMF accrual is IRREVERSIBLE (the contract's index is monotonic). Any suite that
  accrues the shared fixture fund leaves it above par forever, so tests must assert
  invariants (index >= par, shares = value/index, round-trip >= principal) rather than
  par-equality, and a test file that accrues should do it in its LAST block. Vitest
  file order is sequential but NOT alphabetical, so never rely on "my file runs last":
  derive expected amounts from the LIVE index (`valueOfShares(shares, index)` is exactly
  what `redeem` pays), not from par.
- API routes: `route.ts` is the only routable filename, so shared glue colocates fine
  under `app/api/**` (e.g. `app/api/treasury/errors.ts` maps `TreasuryErrorCode` ->
  HTTP status in one place). Keep HTTP concerns out of lib/; keep handlers thin.
- Route tests import the handler directly (`import { POST } from "@/app/api/.../route"`)
  and call it with a `NextRequest` — no HTTP server. A constructed Request with a body
  needs the `{ duplex: "half" }` cast (undici).
- Module import direction inside lib/ is executor → routing → treasury → chain/db.
  Adding an import that points back up the chain (treasury → routing) cycles the graph.
  If two modules need the same fact, put it in the LOWER one and have the higher import
  it (e.g. `parkedBalance` lives in treasury; routing calls it).
- Anything frozen into `Payment.quoteJson` at quote time (route id, fees, and now
  `recall_required`) is a SNAPSHOT — the chain and the DB can move before execution.
  Treat those fields as a hint, and keep the executor's own re-checks. Corollary: a
  helper the executor calls off such a flag should be a safe no-op when the condition
  no longer holds.
- The MMF is backed by mockUSDC only, and the executor reserves the DESTINATION asset.
  So a payment can only exercise MMF liquidity when its destination currency is USD
  (USD→USD is a legal corridor — `midRate` returns 1 when source == dest). A USD→JPY
  payment reserves mockJPY and never touches the fund.
- `scripts/*.mjs` CANNOT import anything from `lib/` (TS, and there is no TS runner —
  no tsx/ts-node installed). Any logic a seed/deploy script shares with lib/ must be
  duplicated inline and kept in sync BY HAND (see setup.mjs's `hashKey`/`generateKey`
  copy of lib/auth.ts). Note the duplication in AGENTS.md when you add one, and
  cross-check it for real — a silent drift here breaks every seeded key.
- Auth identity lives in `lib/auth.ts`: `authenticate(request)` → `Principal | null`
  (`x-api-key` header, then `sos_key` cookie). It types its param as `Request`, not
  `NextRequest`, so route tests can pass a plain `new Request(...)` — NextRequest
  extends Request, so both work. Security helpers should FAIL CLOSED (return null)
  on malformed data rather than throw or grant a partial identity.
- Secrets the app generates (API keys) follow the deployments.json precedent: hash/
  reference in the DB, raw value only in a gitignored `chain/*.json` + printed once
  by setup. `.gitignore`'s `chain/deployments*.json` does NOT cover other chain/
  files — add an explicit line and verify with `git check-ignore -v <path>`.
- Verifying `npm run setup` without destroying dev state (the documented dance):
  back up `chain/deployments.json` + `prisma/dev.db` to /tmp, start both chains
  (`npm run chain`, `npm run chain:polygon`), poll `eth_chainId` on 8545/8546 until
  both answer, run setup, then `pkill -f "hardhat node"` and restore both files.
  The restored dev.db predates any schema change you just made — that is expected;
  `npm run setup` is what re-syncs it.
- Framework-free lib/ modules stay testable: `lib/auth.ts` takes a plain `Request` and
  never imports `next/headers`, so route tests can call it directly. The Next-only glue
  (`cookies()`) lives in a SEPARATE module, `lib/session.ts` (`currentPrincipal()` for
  server components). Follow that split for anything else that needs request context —
  putting `next/headers` in a lib/ module makes it uncallable from plain vitest.
- Route handlers can be tested WITHOUT an HTTP server, including cookies: call the
  handler and read `res.cookies.get(NAME)` off the returned `NextResponse` — it exposes
  `value`/`httpOnly`/`sameSite`/`path`, and a `.delete()` shows up as value `""`.
  A no-arg handler (`POST()`) needs no Request at all.
- EVERY API error body is `{ error_code, message }` (codes in `lib/api-errors.ts`).
  Split by provenance: a message a route CHOSE is safe to ship (`invalidRequest(...)`,
  `conflict(...)`, TreasuryError domain text); a message a THROW carried is not
  (executor/prisma/viem errors name contract addresses, RPC URLs, revert data) — send
  those through `caughtErrorResponse(e, fallback, context)`, which logs the real error
  and answers canned. `(e as Error).message` in a handler is always a bug.
  Clients read `data.message`, never `data.error`.
- Undoing an on-chain step: decide from the CHAIN, not the DB status. lib/chain's
  `onchainPaymentState()` reads the escrow's own `getPayment`; the DB only records what
  an attempt TRIED, and the two disagree exactly when something threw mid-flight (which
  is the only time a recovery path runs). Refund while the escrow is held, compensate
  once it is released — a released escrow cannot be refunded (`failAndRefund` reverts
  "not initiated").
- Failure paths that no input can provoke on a healthy fixture chain get an exported
  `executorTestHooks`-style object of optional throw points (lib/executor.ts). Tests
  assign one and `delete` it in afterEach; nothing in the app ever assigns them. Cheaper
  and clearer than vi.mock of a whole chain module.
- A payment's status changes ONLY via `transitionStatus()` (lib/transitions.ts): it
  asserts the move is legal, then compare-and-swaps on the status the caller observed
  (`updateMany where {id, status: from}`), and audits only if a row actually changed.
  A raw `prisma.payment.update({data:{status}})` is a bug — it clobbers whoever won a
  concurrent race. Corollary: a handler must transition from the row it READ, and the
  executor's `payment = {...payment, ...(await setStatus(...))}` assignments carry the
  expected value, so they are load-bearing.
- A lib error with an obvious client meaning should extend `ApiError` with its code
  (StaleTransitionError -> "conflict") rather than invent a typed code + a per-route
  status table (treasury's older shape). The routes' existing `caughtErrorResponse`
  then renders it — a 409 with no mapping code at all.
- Route handlers must never `await req.json()` bare: an unparseable body becomes an
  unhandled throw that Next renders as a 500 (with a stack, in dev). Always
  `.catch(() => null)` and return a chosen 400.
- Operator-only detail on a row (e.g. `Payment.failureReason`) is scrubbed at the READ
  routes per principal (`scrubFailureReason`), not by mutating the row — and it has to
  be applied in the list view as well as the detail view, or the redaction has a hole.
- Route authorization goes through `app/api/guard.ts`: `requirePrincipal(req)` /
  `requireRole(req, ...roles)` return `Principal | NextResponse`, so every handler opens
  with `const p = await requireX(...); if (p instanceof NextResponse) return p;`. HTTP
  concerns (status codes, bodies) live under app/api, never in lib/auth.ts.
- Security responses stay GENERIC and identical: anonymous == invalid key == 401
  `{error:"unauthorized"}`; another tenant's row == nonexistent row == 404 (never 403,
  which would confirm the id exists). Assert byte-identical bodies in tests, not just
  matching statuses.
- Tenant scoping belongs in the prisma `where` clause
  (`isPlatformRole(p) ? {} : { OR: [...] }`), not a filter over already-fetched rows —
  a row that was never loaded cannot leak via a count, an aggregate, or a new field.
- DELETING A PAYMENT BREAKS THE AUDIT CHAIN. `AuditEvent.payment` is an optional
  relation → Prisma's default `SetNull` NULLs `paymentId` on its events, and paymentId
  is INSIDE the event hash, so every later event fails verification and unrelated test
  files go BROKEN (`verifyAuditChain` → `{valid:false, brokenAtId:N}`). A test that
  cleans up payments must skip the ones that got audited. Symptom to recognize: a chain
  break in a file you did not touch, at a low event id.
- Identity/authz that a route derives from the caller must never be overridable by the
  request body (the review route took `body.reviewer` — a forgeable audit signature).
  Audit with `actorOf(principal)` from app/api/guard.ts; leave machine-initiated events
  (executor, treasury internals) as "system".
- Concurrency control here is always RESERVE-THEN-ACT, never CHECK-THEN-ACT: let the DB
  decide the race (a unique index, or a CAS `updateMany` on the value you observed), then
  do the work you now own. `transitionStatus` (status CAS), the execution lease (CAS on
  `executionLeaseId IS NULL`), and idempotency (unique `(principalId, key)` create) are
  all the same shape. A `findFirst` + `if (!exists)` is a bug — two callers both pass it.
- The `X | NextResponse` return + `if (x instanceof NextResponse) return x` narrowing is
  the house convention for "do the thing, or hand me the response to send" helpers
  (`requirePrincipal`, `authorizePaymentWrite`, `beginIdempotency`). Follow it for new
  route glue rather than inventing a result object or throwing.
- A route wrapper that must cover EVERY exit (idempotency; later: rate limiting) needs
  the handler body as its own function returning a NextResponse — extract
  `POST()` → thin wrapper + `doTheThing(principal, ...)`, rather than threading the
  wrapper through a dozen early returns. Note `req.json()` is a one-shot stream, so read
  the body ONCE in the wrapper and pass it down; to store a response you must
  `res.clone().text()` it.
- Fields on `Principal` come from `principalForKey` (lib/auth.ts) — the ONLY constructor,
  so adding one (e.g. `keyId` for per-caller state) is cheap. But `toEqual` assertions on
  a whole Principal in tests/db/auth.test.ts break on any new field: use
  `expect.any(String)` for ids.
- When a write route adds an authz check, its not-found body must match the READ
  route's byte for byte (both `notFound()` from guard.ts) — a write that says
  "payment not found" while the guard says "not found" re-opens the existence oracle
  the read routes closed.
- Adding auth to a route BREAKS every existing test that calls the handler — they all
  construct requests without a key. Fix at the test's request-builder helper (add
  `[API_KEY_HEADER]: API_KEYS.operator` in one place), not call by call.
- `chain/dev-api-keys.json` maps name -> raw key STRING (`.operator`, not
  `.operator.key`). Reading it wrong yields a literal "undefined" header and a
  confusing wall of 401s that looks like an app bug.
- A dev.db restored by the backup/restore dance predates any schema added since —
  hitting a new table on it 500s ("The table `main.X` does not exist"). That is the
  restore, not your code; `npm run setup` (with both chains up) is the fix.
- To exercise something against the DEV db (not the fixture), write a throwaway
  vitest file that news up its own `PrismaClient({ datasourceUrl: file:<dev.db> })`
  — `setup-env.ts` pins DATABASE_URL to the fixture for every worker, so an explicit
  datasourceUrl is the only way around it. Delete the file afterward.
- A lib error with an obvious client meaning should extend `ApiError` with its code
  (StaleTransitionError, ExecutionLeaseError → "conflict"). Routes need NO mapping:
  the existing `caughtErrorResponse`/`fromThrown` passes an ApiError's code + message
  straight through. Reserve treasury's typed-code + per-route status table for errors
  whose HTTP meaning is route-dependent.
- Guarding a side-effecting operation against concurrency: the status you READ is
  already stale — the CAS that claims the work is what decides the race, and it must
  come BEFORE the first irreversible effect (a chain write), not just before the DB
  write. Anything claimed must have a release path for throws that never reach the
  code that would normally release it (a `finally`, scoped to the claim's own id so
  it cannot free a later claim).
- Naming a relation-included Prisma row at a function boundary (to extract a helper
  out of a long function) needs `Prisma.PaymentGetPayload<{ include: {...} }>` —
  findUniqueOrThrow's inline inference does not survive being passed as a param.

  - RESERVE-THEN-STAMP was the whole design decision. The obvious shape — look the key
    up, and if it is absent run the handler — is exactly the check-then-act bug the CAS
    stories (US-006/US-007) already outlawed: two duplicates both find nothing and both
    run. Creating the record FIRST makes the unique index the arbiter, and the record's
    own state then answers every duplicate: unstamped -> 409 in-flight, stamped ->
    replay, different body/route -> 422. This codebase now has three instances of the
    same pattern (status CAS, execution lease, idempotency) — reach for it by default.
  - The two ACs pushed in different directions on WHAT to store. Storing only successes
    would leave a definite failure (a 409 from a bad status, a 500 execution_failed)
    retryable-but-not-replayable, which contradicts "same key + same body replays the
    stored response". Resolution: store whatever the handler RETURNED (errors included —
    a definite answer is an answer), and abandon the key only when the handler THREW,
    because an unknown outcome is the one case where re-running is the honest move.
  - `route` must be the CONCRETE path, not the template. `POST /api/payments/[id]/execute`
    as the stored route would let one key aimed at payment A replay its response for
    payment B — a silent wrong answer. Storing `POST /api/payments/pay_x/execute` turns
    that into the 422 it is. Anything a route's identity depends on but the body does not
    carry (a path param) has to be in `route` or in the hash.
  - JSON.stringify is NOT a request fingerprint: its key order is insertion order, which
    a client does not control, so `{a,b}` and `{b,a}` would 422 as "different requests".
    Canonicalize (recursive key sort) before hashing.
  - Expiry needed the CAS treatment too: two callers presenting the same aged-out key
    would otherwise both reclaim it. `updateMany where {id, createdAt: <the value I read>}`
    makes exactly one the owner. The begin loop is bounded at 2 passes — the row can be
    abandoned or reclaimed between our failed create and our read, but a second failure
    means someone holds a live reservation, which IS the in-flight answer.
  - Extracting the handler body (POST → thin wrapper + createPayment()) was the only way
    to make the scope cover every exit. Watch the types when you do it: `req.json()`
    returns `any`, so the destructuring inside the old handler type-checked on nothing;
    the extracted function needs a real param type (an all-optional interface documents
    "unverified until validated" honestly — `Record<string, unknown>` will NOT compile
    against `NETWORKS[source_network]`).
  - Prisma unique-violation detection: catch and check `e.code === "P2002"` (no import of
    Prisma.PrismaClientKnownRequestError needed). Rethrow anything else — swallowing it
    would turn a real DB fault into a silent duplicate run.
  - `res.clone().text()` to store a response body: the stream is one-shot and the caller
    still needs it. Same reason the wrapper reads `req.json()` once and passes it down.
  - Adding a field to Principal broke two `toEqual` assertions in tests/db/auth.test.ts
    (nothing else — principalForKey is the only constructor). Cheap, but grep for
    whole-object assertions before assuming a type-level change is free.
